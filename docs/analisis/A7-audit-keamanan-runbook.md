## 1. Matriks Temuan Audit pada `docs/11` (Threat Model) dan `docs/12` (Runbook)

| ID | Dokumen & Bagian | Asumsi Saat Ini | Kelemahan / Kesalahan Teknis | Rekomendasi Perbaikan & Status |
| :---: | :--- | :--- | :--- | :--- |
| **T-01** | `docs/12` ("Prosedur rilis: `pm2 reload jr-api`") & "PM2 (`ecosystem.config.cjs`)" | `jr-api` dijalankan dengan `instances: 1` (mode `fork` default PM2), lalu prosedur rilis menjalankan `pm2 reload jr-api`. | Pada PM2, `pm2 reload` (zero-downtime reload) **hanya bekerja pada `exec_mode: 'cluster'`**. Pada mode `fork` dengan `instances: 1`, `pm2 reload` jatuh kembali (*fallback*) ke `restart` yang memutus koneksi aktif sesaat, atau gagal jika sinyal `SIGINT` tidak ditangani oleh Fastify (`app.close()`). | 1. Tambahkan penanganan *graceful shutdown* (`SIGTERM`/`SIGINT` -> `fastify.close()`) di `apps/api` pada M2.<br>2. Di `ecosystem.config.cjs`, gunakan `exec_mode: 'cluster'`, `instances: 2` (atau `1` dengan `wait_ready: true, listen_timeout: 10000, kill_timeout: 10000`) untuk `jr-api`. Untuk `jr-worker`, **wajib tetap `instances: 1, exec_mode: 'fork'`**. |
| **T-02** | `docs/12` ("nginx (sketsa)") | `proxy_set_header X-Forwarded-For $remote_addr;` tanpa konfigurasi `trustProxy` dan tanpa batas ukuran body (`client_max_body_size`). | 1. Jika Fastify tidak dikonfigurasi dengan `trustProxy: '127.0.0.1'`, semua request terlihat berasal dari `127.0.0.1`, sehingga **rate limit per IP akan memblokir seluruh pemain sekaligus**!<br>2. Sebaliknya, jika `X-Forwarded-For` diteruskan mentah tanpa ditimpa oleh `$remote_addr` pada reverse proxy tepercaya, penyerang dapat memalsukan header `X-Forwarded-For` untuk melewati rate limit.<br>3. Tanpa `client_max_body_size 64k;` dan `proxy_read_timeout 15s;`, penyerang dapat mengirim payload JSON raksasa ke parser DSL. | Di `docs/12`, tambahkan `client_max_body_size 64k;`, `proxy_set_header X-Real-IP $remote_addr;`, dan catatan bahwa `apps/api` wajib menyetel `trustProxy: '127.0.0.1'`. Tandai lokasi berkas vhost nginx sebagai `[PERLU VERIFIKASI PEMILIK]`. |
| **T-03** | `docs/11` (T5: "Multi-akun: Verifikasi email, rate limit pendaftaran per IP") vs `docs/02` & Keputusan Pemilik | `docs/11` mengasumsikan "Verifikasi email" sudah ada untuk mencegah *multi-account farming*, padahal di MVP belum ada layanan pengiriman email (SMTP/transaksional) dan verifikasi email masuk daftar **Keputusan Pemilik**. | Jika verifikasi email dinonaktifkan di MVP (untuk mempermudah onboarding < 3 menit), kontrol anti-multi-akun yang tersisa hanyalah rate limit per IP dan ketiadaan fitur transfer koin langsung antar-pemain. Namun melalui manipulasi harga di pelabuhan sepi (*wash trading* komoditas stok tipis), akun boneka masih berpotensi menyubsidi akun utama jika dibuat massal. | 1. Pisahkan kontrol T5 di `docs/11` menjadi kontrol **wajib MVP tanpa SMTP** (rate limit pendaftaran ketat `5/jam/IP` + `20/hari/subnet /24`, larangan transfer langsung, biaya pelabuhan 2% dua arah yang membuat *wash trading* rugi bersih $\ge 4\%$, deteksi korelasi perdagangan berulang antar dua akun di pelabuhan yang sama) dan kontrol **opsional di balik flag `REQUIRE_EMAIL_VERIFICATION`** (keputusan pemilik). |
| **T-04** | `docs/11` (T14: "Spam/penyalahgunaan simulasi") & `docs/08` ("Batas laju") | `docs/12` hanya memasang `limit_req` nginx pada `/v1/auth/`, sedangkan `/v1/simulate` (CPU-bound, 200 tick) dan `PUT /v1/ships/:id/rules` dibatasi per **pemain** (`10/menit/pemain`), bukan sekadar per IP. | Nginx tidak mengenali `player_id` di dalam JWT tanpa modul khusus, sehingga jika rate limit `/v1/simulate` hanya mengandalkan nginx per IP, satu akun jahat di balik NAT seluler operator Indonesia (CGNAT, ribuan pengguna berbagi 1 IP publik) akan memblokir pemain lain, atau penyerang multi-IP dapat membebani event loop Node.js. | Tegaskan di `docs/11` dan `docs/12`:<br>1. Rate limit `/v1/auth/*` menggunakan kombinasi IP + email di lapis aplikasi (`@fastify/rate-limit` atau limiter in-memory berbatas LRU) + pelindung kasar di nginx.<br>2. Rate limit `/v1/simulate` (`10/menit/player_id`) dan `PUT /v1/ships/:id/rules` (`30/menit/player_id`) ditegakkan **per `player_id` setelah verifikasi JWT** di `apps/api`, disertai *concurrency semaphore* (maksimal 2 simulasi berjalan paralel di API). |
| **T-05** | `docs/12` ("Cadangan dan pemulihan: `pg_dump -Fc jalurrempah > backup_YYYYMMDD.dump`") | Menyimpan dump di disk VPS lalu "salin ke lokasi luar VPS", tanpa merinci proteksi izin berkas, rotasi lokal, dan konsistensi dengan transaksi tick. | 1. `pg_dump` berjalan di bawah transaksi `REPEATABLE READ` sehingga aman secara konsistensi walaupun worker sedang berjalan, **tetapi** berkas `.dump` berisi `password_hash` dan email pemain; jika disimpan dengan izin default `0644` di `/tmp` atau direktori bersama, user lokal lain di VPS dapat membacanya.<br>2. Jika disk VPS penuh karena retensi lokal tidak memakai `find ... -mtime +14 -delete`, PostgreSQL akan berhenti menulis WAL dan seluruh dunia macet. | Perbarui `docs/12` agar menggunakan `umask 077`, direktori khusus berizin `0700`, pengecekan ukuran berkas non-nol, serta penghapusan otomatis dump lokal $> 14$ hari. Lokasi penyimpanan luar VPS ditandai `[PERLU VERIFIKASI PEMILIK]`. |
| **T-06** | `docs/12` ("Komponen di VPS: Port 3100, PostgreSQL 5432, nama DB `jalurrempah`") | Menyebut `PORT_API=3100`, port PostgreSQL `5432`, dan konfigurasi vhost nginx secara langsung. | VPS pemilik mungkin sudah menjalankan layanan web, reverse proxy, atau instance PostgreSQL lain pada port tersebut. | Dipertahankan sebagai contoh dengan penanda eksplisit **`[PERLU VERIFIKASI PEMILIK]`** dan daftar perintah pemeriksaan pra-instalasi (`ss -tulpn`, `psql -l`, `nginx -T`) sebelum menyentuh konfigurasi VPS. |
